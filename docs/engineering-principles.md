# Інженерні правила Rust

Статус: правила реалізації та її review. Користувач уже дозволив production-порт
і попросив припинити розширення probes; правила застосовуємо в коді, а не
використовуємо як привід відкладати реалізацію до закриття всіх досліджень.

## 1. Що переносимо, а що проєктуємо заново

**Зберігаємо погоджену поведінку, а не структуру legacy-коду.** `main` — джерело
відомостей про наявні функції, формати, налаштування та крайові випадки, але не
еталон архітектури. Не робимо механічного перекладу C#/Python на Rust.

- Контракт поведінки: [behavior.md](behavior.md), включно з явно погодженими
  відмінностями; defaults: `../crates/core/assets/default-settings.json`.
- Структура: [architecture.md](architecture.md).
- Legacy-тест, який перевіряє бізнес-правило, переносимо за змістом. Тест, який
  прив'язаний до WPF-класу, приватного поля чи старої файлової структури,
  переписуємо під нову межу, а не відтворюємо стару реалізацію заради тесту.
- Виявлений дефект записуємо окремо від вимоги. Не копіюємо його мовчки та не
  змінюємо видиму поведінку під виглядом «чистої архітектури» без узгодження.

## 2. Модульність: правила залежностей

Кожен модуль має одну зрозумілу відповідальність, явний публічний контракт і
власника ресурсів. Сусідні модулі не читають його внутрішні поля та не обходять API.

| Шар | Відповідає за | Чого не повинен знати |
| --- | --- | --- |
| Domain / `core` | Стани, інваріанти, типи налаштувань, правила переходів | GPUI, Win32, файлову систему, мережу, процеси, CT2/ORT |
| Application | Сценарії диктування, settings/model lifecycle, виконання рішень domain через вузькі порти | Конкретні GUI, HTTP, audio, IPC transport чи ML-бібліотеки |
| Protocol | Версіоновані повідомлення host ↔ worker, wire DTO, обмеження формату | UI-стан, запуск процесу, inference, користувацькі діалоги |
| Adapters | Реальне audio, Win32, UI, storage, download, worker transport, native inference | Внутрішні деталі інших адаптерів; не визначають бізнес-правила |
| Composition root | Побудова конкретних залежностей, під'єднання runtime, start/stop | Сам не реалізує диктування, decoding, збереження чи UI-логіку |

Напрям залежностей — **від зовнішніх реалізацій до внутрішніх контрактів**, а не
навпаки. Конкретні адаптери з'єднуються в composition root. UI не викликає
безпосередньо CT2, Win32 paste або конфігураційний файл: передає команду application
і відображає отриманий стан. Внутрішні шари не викликають UI для показу помилки.

Порти визначає споживач. Host-application визначає потрібний йому контракт
транскрипції; worker adapter реалізує його через IPC. Wire DTO перетворюються
на application-типи на межі, а не стають моделлю всього застосунку.

Початкова пакетна схема — `core`, `application`, `protocol` та два executable:
host і worker. UI/audio/storage/models/platform спочатку можуть бути окремими
модулями адаптерів host. Новий crate потрібен для реальної ізоляції залежностей,
окремого тестування/збирання чи повторного використання — не для кожного trait.
Циклів між шарами немає, навіть якщо частина меж поки всередині одного crate.

## 3. SOLID без перенесення OOP-шаблонів у Rust

| Принцип | Правило для цього проєкту |
| --- | --- |
| **S — Single Responsibility** | State machine вирішує допустимий перехід; audio adapter записує; config repository читає/пише; UI малює. Один controller не поєднує все це. Файл або тип ділимо за незалежними причинами зміни, а не довільною кількістю рядків |
| **O — Open/Closed** | Заміна реалізації audio/platform/STT не потребує переписування сценарію диктування. Розширення має йти через наявну змістовну межу. Не будуємо plugin framework «на майбутнє» |
| **L — Liskov Substitution** | Реальний адаптер і fake виконують однаковий контракт: значення результату, помилки, порядок завершення, cancellation і cleanup. `cudaOnly` не може непомітно перейти на CPU, а прийнятий запит не може загубитися без результату чи помилки |
| **I — Interface Segregation** | `AudioCapture`, `Transcription`, `SettingsRepository`, `Paste` — окремі невеликі контракти за потребами споживачів, а не один `PlatformService` на десятки операцій. Не додаємо методів, які реалізації змушені ігнорувати |
| **D — Dependency Inversion** | Application залежить від власних портів; Win32/GPUI/CT2 adapter залежить від цих контрактів. Конкретні залежності передаються явно через конструктори/параметри, без service locator або глобального singleton |

У Rust використовуємо композицію, `struct`, `enum`, pattern matching і traits
там, де вони виражають реальний контракт. Не створюємо ієрархій «base service».
Для чистої функції trait не потрібний; для фіксованого набору станів `enum`
часто простіший за trait objects. `dyn Trait`, generics і async-форму портів
обираємо за потребами runtime та тестів, не як універсальний стиль усіх модулів.

## 4. DRY: одне джерело знання, не одна універсальна функція

- Один набір типів повідомлень IPC; не дублюємо JSON-схему в host і worker.
- Одна канонічна валідація налаштувань, яку використовують і UI Save, і config load;
  UI може мати попередні підказки, але не власні суперечливі правила.
- Defaults задаються в одному місці та перевіряються fixture зі збережених settings;
  не розносимо копії prompt/model/device по UI, worker і build scripts.
- Значення model ID, revision та hashes мають канонічний manifest. Build і runtime
  не підтримують незалежні неузгоджені списки моделей.
- Бізнес-правило повторних спроб, fallback або cleanup має одного власника на
  відповідній межі. Не вкладаємо однаковий retry у UI, application і adapter,
  множачи число фактичних спроб.
- Не зливаємо різні політики лише через схожі рядки коду: retry clipboard і retry
  download — різні задачі; domain-тип та wire DTO можуть свідомо відрізнятися.
- Витягуємо спільну абстракцію, коли спільним є **правило**, а не випадкова форма.
  Невелике повторення зрозуміліше за передчасний generic «універсальний manager».

## 5. KISS і YAGNI

Обираємо найпростіше рішення, яке виконує поточні вимоги й дозволяє його перевірити.

- Прямі типізовані виклики всередині процесу; локальний IPC лише між host і worker.
  Немає потреби в HTTP-сервері, мікросервісах чи message broker.
- Явні команди/події диктування замість глобального event bus або framework
  виконання довільних effects. Не маскуємо залежності через `Any` чи string keys.
- Без DI-контейнера, repository для кожного типу, власного async runtime,
  багатошарових wrapper-ів над одним методом або універсальних plugin API.
- Cross-platform seam потрібний; реалізація невикористаних macOS/Linux adapters
  зараз не потрібна. Не пишемо фіктивні «успішні» заглушки для непідтриманих дій.
- Не вводимо додатковий процес, потік, crate або залежність без конкретної причини.
  Окремий STT worker обґрунтований ізоляцією native crash і керуванням ресурсами.
- Performance-ускладнення вводимо після вимірювання; bounded audio path та
  неблокуючий UI — базові вимоги коректності, а не привід для загального framework.

## 6. Стан, асинхронність і ресурси

- Канонічний стан сценарію має одного власника. UI отримує read-only view/projection,
  а не веде незалежні `isRecording/isBusy/modelLoaded` як друге джерело істини.
- Переходи та рішення domain тестуються без GUI/IO. Application організовує
  побічні дії та повернення результатів; adapters не змінюють стан потайки.
- `SessionId`, `RequestId`, `WorkerGeneration` — різні типи, не взаємозамінні числа.
  Кожне асинхронне завершення перевіряється на актуальність до зміни стану чи paste.
- Не тримаємо mutex/borrow під час `await`, IPC, UI dispatch або чужого callback.
  Канали та буфери мають межу й визначену реакцію на переповнення.
- Audio/hook callbacks виконують мінімальну обмежену роботу: без блокування,
  файлового/мережевого IO, inference або необмежених алокацій і логів.
- Ресурс має явного власника: recording володіє temp-аудіо; worker manager —
  процесом, job і pipes; adapter — своїм hook/registration; download — partial files.
- `Drop`/RAII використовуємо для синхронного звільнення; асинхронне завершення
  має окремий явний `shutdown/stop` зі строком очікування та передбаченим cleanup.
  Не припускаємо, що `Drop` сам дочекається async-роботи.
- Фонові задачі мають власника, cancellation/join policy і шлях повідомлення помилок.
  Не залишаємо fire-and-forget задач, які живуть довше за свою сесію чи вікно.

## 7. Помилки, безпека й стиль Rust

- На межі adapter перетворює Win32/native/transport errors на змістовні типізовані
  помилки. Application визначає реакцію; UI перетворює її на повідомлення.
- Очікувані відмови не спричиняють panic. У production-шляхах немає безпідставних
  `unwrap/expect`, мовчазного ігнорування `Result` або підміни помилки успіхом.
- Не додаємо мовчазний CPU fallback, AppData fallback чи пропуск VAD заради
  «стійкості». Відновлення виконує погоджений контракт, а не змінює його.
- `unsafe`/FFI зосереджені в невеликих adapters, з описом lifetime/threading і
  safety-invariants. Native handles не виходять у domain/application.
- Валідуємо IPC, шляхи та конфігурацію на межах; після цього використовуємо
  валідовані типи. Логи не розкривають transcript/prompt за замовчуванням.
- Ідіоматичні назви Rust, вузька видимість (`pub(crate)`/private), `rustfmt`,
  `clippy`. Дозвіл lint має локальну причину; не вимикаємо перевірки глобально.
- Коментар пояснює причину чи інваріант, а не переказує очевидний код.

## 8. Тести та критерії review

Тестуємо поведінку на правильному рівні, а не кількість класів/trait-ів.

1. **Domain/application:** deterministic unit-тести переходів, cancel, stale events,
   defaults, settings changes, paste policy; fake ports без Windows, GPU та мережі.
   Час передаємо явно або через вузьку testable clock-межу; не тестуємо debounce
   очікуванням реального `sleep` у unit-тестах.
2. **Контракти:** однакові гарантії fake/real adapters, schema/version/size limits
   IPC, відповідність фактичних inference-параметрів узгодженим.
3. **Adapter integration:** filesystem/Win32/audio/native lifecycle, failures і
   cleanup — окремі opt-in перевірки з контрольованими ресурсами.
4. **Продукт:** погоджена feature parity та наскрізна диктовка. Успішний unit-тест
   не доводить реальну вставку, CUDA-продуктивність чи відсутність крадіжки фокуса.

Перед прийняттям зміни перевіряємо:

- [ ] Відповідальність і напрям залежностей зрозумілі; циклів/обходу меж немає.
- [ ] Бізнес-правила не розміщено в UI, transport або FFI callback.
- [ ] Публічний API мінімальний; нова абстракція має поточне обґрунтування.
- [ ] Немає дубльованого джерела defaults, validation, стану чи retry policy.
- [ ] Власник, cancellation, stale-event handling і cleanup визначені.
- [ ] Є тести потрібного рівня; відомі неперевірені твердження названі прямо.
- [ ] Збережено погоджену поведінку або явно описано відмінність.
- [ ] `fmt`, `clippy` і релевантні тести пройдено, коли реалізація вже існує.

Це не вимога створити весь каркас наперед. Після дозволу на реалізацію рухаємося
невеликими перевірюваними вертикальними кроками; не копіюємо disposable-прототип
у production без звичайного review цих правил.

## 9. Межі досліджень і постійні настанови

Експеримент повинен мати конкретне питання, мінімальний обсяг і критерій зупинки.
Не перетворюємо другорядну перевірку на продукт. Якщо вимогу знято або досягнуто
межі експерименту, записуємо результат і зупиняємось; не нарощуємо harness за інерцією.

Стислий набір постійних правил є в кореневому [`AGENTS.md`](../AGENTS.md).
Детальні правила залишаються тут. Історичні legacy-описи не визначають
архітектуру чи defaults Rust-версії.

## 10. Settings UI: обов'язковий спеціалізований контракт

Перед змінами Settings/layout/render/scroll/DPI/event lifecycle прочитати
[settings-ui-engineering.md](settings-ui-engineering.md): source-linked
правила з Zed і конкретні дефекти нашого поточного шляху. Користувацький масштаб
175% є основним acceptance target. Ні тести без реальних resize/drag подій, ні
статичний screenshot не закривають flicker, blur та responsiveness failures.
Не змішувати layout/render/input ownership і не тримати borrow через reentrant
Win32/default-handler виклики. Стислий постійний checklist є в `AGENTS.md`.
